What?

Lens 01 · What

The thing itself

te9-docs is a document-suite skill: it produces polished, shareable, single-file HTML documents for human readers — and every one of them is written in the Clay Explainer design system.

Concretely, it lives in the skills.te9.dev repo as a plain-dir Agent Skill (agentskills.io conformant), packaged for the pi agent as a thin plugin wrapper. Its unit is the Template — a finished, full-HTML document with realistic placeholders — and its product is the Document: the instance a reader actually receives. The launch taxonomy counts 36 types, from decision brief to cashflow statement.

"Single-file" is a commitment, not a slogan: the three type faces ride as system stacks — zero webfonts, zero network requests in every document; folds are <details>, jumps are :target, and there are zero scripts by default under Clay discipline. A Document is one file that opens from disk anywhere, with dark mode, the print spec and AA contrast riding along in the tokens.

Example · one WHAT, three times over
The founding trio

brief.html (decision brief), dossier.html (evidence dossier) and deck.html (presentation deck) — the three founding documents, converted from the examples with placeholders rewritten about the suite. Three files, three purposes, one design system; each opens from disk with zero requests.

How?

Lens 02 · How

The production run

One document, one ordered run: Intake → Index-first → Instance → Figures → Playback → Storage menu — six steps, always in that order.

Intake asks for the document's goal and acceptance criteria, and states the session's own recommendation — type and approach — from context. Index-first reads the suite index (assets/templates/index.json), normative for discovery, and grounds the type decision in it; the user confirms if two types could match. Instance copies the chosen Template and swaps the self-describing placeholders for real facts, preserving layout, interactions, and Clay tokens.

Figures render at build time — Mermaid source through pele, clayified into the ring grammar, inlined in a fenced gray-100 plate with a mono FIG · NN caption. Playback shows the document in the browser — the review gate, approval after each build, feedback folded in on the spot. The Storage menu closes the run: (a) the project's docs folder, (b) the central collection at E:\te9-docs\documents\, (c) preview only — and the fourth option, specify a location, always wins when used.

Example · a run in miniature
Six steps, one Document

A session is asked for a concept breakdown. Intake fixes the goal; the index says 05-concept-breakdown.html matches; the Template is copied and its suite placeholders swapped for the reader's facts; the anatomy figure is rendered via pele and clayified; the build opens in the browser and passes the gate; the file lands at <project>/docs/<YYYY-MM-DD>-<slug>.html.

Why?

Lens 03 · Why

The reason it exists

So that polished, consistent documents happen without design work — the design decisions are made once, in one design system, and every document inherits them.

The Clay Explainer design system was extracted from the founding examples and specified in references/CLAY-STYLE.md: warm ivory ground, 1.5px hairlines, mono pill kickers, giant serif headlines with one italic clay word. Because all 36 types draw the same tokens, the same ring grammar and the same section rhythm, the suite reads as one publication — no document looks like its author invented a style that morning.

And the patterns are owned: te9-docs is the clean-room sibling of the vendored html-docs skill — every pattern adopted from it was re-justified and is owned as a te9 signature, with the decisions recorded in docs/adr/0001–0006. Ownership is what makes the polish a property of the suite rather than of whichever session happens to be building.

Example · what the reader gets for free
Hand over the file

A Document handed to a human reader needs no instructions: it opens offline (zero network requests), flips dark with their OS preference, prints quiet with every fold forced open, and every accent passes AA. All of it arrives through the tokens — nobody designed anything to earn it.

Who?

Lens 04 · Who

The hands and the eyes

Any agent session builds; human readers outside the session read — and the two never need to meet.

The build side is written for a session, not a designer: intake, the index and the Template mechanic are executable by any agent session, with no design judgment required. Even growth is autonomous — the extension protocol lets a session that needs an unlisted type build it to the same conventions (Clay, self-describing content, whitelist compliance, quality gates), save it to assets/templates/, register it in the index, bump the suite version and write its own changelog line.

The read side is a human outside the session: they receive one file — no fonts to load, no scripts to run, no network to reach. The review gate keeps that human in charge of what ships: the document is shown in the browser after each build, and feedback is folded in while the session is still open.

Example · the extension protocol, meeting a missing type
A type that wasn't there

A session is asked for a project postmortem. The index lists 36 types — none of them is a postmortem. The session builds one to the same conventions, registers it in the index, bumps the suite version by a MINOR and appends the changelog line. The next session discovers the new type where all types live: the index.

When?

Lens 05 · When

The moments it serves

Whenever something must leave the session and reach a human — whenever a shareable artifact is needed.

The trigger is a shareable artifact; the check is the index. It grounds which of the 36 types fits the moment: a concept breakdown for one concept's anatomy, a 2D quadrant overview for positioning, timelines and steps for a plan, API documentation for an interface, a cashflow statement for the money. The index is normative for discovery — there is no keyword heuristics file to guess from.

The second when is whenever a type is missing — the extension protocol's trigger, and the version answers for it: a new template bumps the suite MINOR, a template or convention fix bumps PATCH, a breaking change bumps MAJOR, and every bump appends a one-line changelog entry. The user discovers new types in the index next session.

Example · the two-question WHEN test
Before reaching for the suite

Does this need to reach a reader outside the session? If no, stop — the suite produces documents for humans, not notes for the session itself. If yes: does a type exist in the index? If yes, instance it; if no, build the type, register it — and the next "when" is already covered.
