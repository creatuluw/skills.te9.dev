The parts

Six parts, each taken in depth

Each panel below takes one part of the Template instance: a definition lede worded from the suite's glossary, the behavior as the production run actually executes it, and — folded open — one edge case or misconception. Every fact comes from the suite brief; nothing here is invented.

Part 01 · Where it begins

The copy step

The instance begins as a literal copy of the Template — a finished, polished, full-HTML document with realistic placeholders — never a rebuild and never a component kit.

A production run reaches the copy only after its first two steps. Step 1, Intake: the document's goal and acceptance criteria are asked for, and the session states its own recommendation — type and approach — from context. Step 2, Index-first: the suite index (assets/templates/index.json) grounds the type decision, with the user confirming if two types could match. Step 3, Instance: the chosen Template is copied.

The copy arrives complete. Every Clay token, fold, pill and hairline of the Template is already in place; the instance's work from here is content, not construction.

Edge case · the copy waits for a confirmed type
Order of operations

The copy is never the first move. If two types could match, the user confirms the type first — only then is a Template copied. The unit being copied is one of the suite's 36 finished types, which is exactly why the confirmation matters: copying the wrong Template is the one mistake the later steps cannot undo.

Part 02 · What changes

The content swap

The swap replaces the Template's self-describing placeholders with the reader's real facts — definitions worded to the suite's glossary, nothing invented.

Placeholders are self-describing: they document the suite itself, so swapping means reading them, keeping their structure, and replacing the suite's facts with the document's own. Definitions are quoted word for word from the glossary — Template, Document, Intake, Review gate, Storage menu — used in their glossary sense, nowhere redefined.

The facts come from one place: the suite brief. It is the single source of truth for placeholder content, and a swap that asserts something the brief does not is out of contract.

Misconception · "the swap is a place to improve the writing"
What the swap touches

The swap is where you rewrite the document's voice, tighten its ledes, improve its design. No — the swap touches content only. Voice, structure and design belong to the Template, and reach instances only through a new Template version, never mid-swap.

Part 03 · What stays

The preserved contract

Layout, interactions and Clay tokens are preserved through the swap — the invariant the suite brief writes into the Instance step in one breath: "preserving layout, interactions, and Clay tokens."

Preserved, concretely: the layout — grid, section rhythm, panel anatomy; the interactions — <details> folds, :target jumps, hover states, with zero scripts by default under Clay discipline; and the Clay tokens — ivory ground, 1.5px hairlines, mono pill kickers, the ring grammar, the dark-mode flip and the print spec.

Break any one of the three and the artifact stops being a te9-docs Document: it may still be an HTML file, but it is no longer a sibling of the founding trio.

Edge case · dark mode and print ride along for free
Why content swaps can't break them

The palette is token-based: the dark flip under prefers-color-scheme and the full print spec are properties of the tokens, not of the content. A swap that changes facts but not tokens inherits dark mode, print behavior and contrast guardrails unchanged — which is why token edits are the one swap the contract forbids.

Part 04 · What is rendered

The figure pipeline

Figures are not drawn into the instance — they are rendered at build time: Mermaid source → pele render (Node) → clayify post-processing → one inline SVG in a fenced gray-100 plate with a mono FIG · NN caption.

pele gives layout — node positions and routed edges. clayify restores the Clay ring grammar on top: uniform ring radii, mono labels outside the rings, sub-labels beneath, supporting nodes as small gray dots, captioned hairline edges with no arrowheads, an optional legend row. The SVG ships inline with the Clay palette mapped onto pele's CSS variables — never with hex values rewritten by hand.

And the figure renders at natural pele scale: the plate's SVG keeps width:auto, centered, shrinking only to fit — labels hold their size in every figure, and no diagram is ever stretched to plate width.

Edge case · the fullscreen view is Clay-correct too
Why the new tab still looks right

clayify embeds the Clay text styles and the dark flip inside the SVG itself. The FULLSCREEN pill opens the diagram in a new tab via a Blob URL — with no document stylesheet present — and the standalone view still reads Clay: mono labels, hairline edges, correct ink in dark mode.

Part 05 · Who sees it

The gate pass

After the build, the instance is shown in the browser and the reader approves or gives feedback — the review gate: browser approval after each build.

This is the production run's playback step. The freshly built document is shown in the browser; the reader's feedback is folded in on the spot, while the session is still open. The gate is per build — each instance passes its own gate, never a batch verdict — and the run only moves on to storage once it has passed.

The gate is also where an instance teaches its Template: what the reader corrects here is a fact about the Template it was copied from.

Misconception · "the gate can be skipped when the build looks right"
No path around it

If the instance looks right, storage can happen without the gate. No — the workflow is ordered: playback (step 5) precedes the storage menu (step 6), and the gate is the playback. A build that was never shown was never approved, and storage has nothing approved to store.

Part 06 · Where it lands

The storage menu

Once the gate passes, the Document is offered a place to live — four options, and the fourth always wins when used.

The menu, verbatim from the brief: (a) the project's docs folder, named <project>/docs/<YYYY-MM-DD>-<slug>.html; (b) the central collection at E:\te9-docs\documents\; (c) preview only, no copy kept; (4th) specify a location — which always wins when used.

The menu is what turns an instance into a Document with an address: from here it is out of the session's hands and in a reader's.

Edge case · the fourth option's precedence
Precedence, not preference

Options (a)–(c) are standing offers; option 4 — specify location — is not a fourth peer but an override: it always wins when used. A reader who names a path ends the menu in one move, and the Document goes exactly there.

Misconceptions

Three things this concept is not

The Template instance collects misconceptions the way a load-bearing wall collects cracks — small, plausible, structural. Each one below is struck through on the left and corrected in body ink on the right.

Misconception

A Template is a skeleton you fill in.

Instead

A Template is a finished, polished, full-HTML document with realistic placeholders — the suite's unit, not its scaffolding. An instance copies a working document, never a wireframe; that is why the copy step can preserve everything and still have nothing left to build.

Misconception

The instance step is where you redesign.

Instead

The swap is never the place to redesign — layout, interactions and Clay tokens are preserved by definition. A design improvement is a change to the Template itself, versioned as a template fix, and only then does it reach every instance born afterwards.

Misconception

Figures are drawn by hand in the finished file.

Instead

Figures are rendered, never drawn: Mermaid source goes through pele at build time, clayify restores the ring grammar, and the finished file carries only the inline SVG. Hand-editing the SVG's geometry or colors is out of contract — the sources in assets/figures/ are the figure.

How the parts compose

The run order

Read the six parts as one sequence — the order a production run executes them, from the copy to the stored Document. The figure showed the shape; this is the same anatomy in time.

  1. 01

    The copy step — a Template, copied whole

    After Intake confirms the goal and Index-first grounds the type, the chosen Template is copied — finished layout, finished interactions, finished tokens, all of it already working.

  2. 02

    The content swap — placeholders become facts

    Self-describing placeholders are replaced with the reader's real facts, definitions worded to the glossary, sourced from the suite brief alone.

  3. 03

    The preserved contract — the invariant throughout

    Not a step so much as a rule the other steps execute under: layout, interactions and Clay tokens stay untouched from the first copy to the last swap.

  4. 04

    The figure pipeline — rendered at build time

    Mermaid → pele → clayify → inline SVG at natural size in its fenced plate, captioned FIG · NN, fullscreen-safe by embedded Clay styles.

  5. 05

    The gate pass — shown, approved, feedback folded in

    The document is shown in the browser after the build; the reader approves or gives feedback, and the feedback is folded in before the run moves on.

  6. 06

    The storage menu — where the Document lands

    Project docs folder, central collection, or preview only — with option 4, specify a location, which always wins when used. The instance leaves the session as a Document.

One subject, six parts, one invariant: an instance is a Template with new facts — nothing more, nothing less. That restraint is the whole mechanic, and it is why the suite's 36 types still read as one publication.
