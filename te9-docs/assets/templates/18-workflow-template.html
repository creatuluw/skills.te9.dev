Roles

Two pairs of hands

Every step in this procedure is owned by exactly one of two roles. Read the four cells below once — they teach the anatomy every step row shares — and the rest of the document parses itself.

Role

The chip on the step names the one who acts — you or the session. One owner per step; never both, never neither.

Action

What gets done, in one line. A step starts when the previous step's verify line reads done.

Verify

The mono line to the right: done when … — the step's own exit test, checkable in the conversation.

Checklist

Each phase closes with static boxes — empty until every verify line in the phase holds. They print as drawn; no state is tracked here.

YOU

decides · reviews · approves

The human half of the pair

Owns the goal, the gate and the home. You state what the document is for, confirm what it will be, pass judgment on what was built, and choose where it lives. The run starts with you and ends with you.

holds · the goal, the review gate, the storage choice

THE SESSION

asks · builds · shows

The agent half of the pair

Does the building. Asks when the ask is unclear, states its own recommendation before grounding it, builds to the conventions, and shows the result before anything is stored — it copies nothing until you confirm.

holds · the recommendation, the build, the playback

Why every step carries a verify line
The discipline behind the mono lines

A step without "done when" is not a step — it is an intention. The verify line makes each step's exit checkable in the conversation itself: the goal is written down, the type points at an index entry, the document is open in your browser.

It is also the pair's contract. The review gate is the suite's own rule — nothing stores before approval — but a gate only works if every step before it declared what "done" means. When a verify line can't read done, the step is not finished, whatever was built.

Phase 01 · Ask & align 4 steps · you open it, the session grounds it, you close it

Agree what done means, before anything is built

No writing happens in this phase. Its output is a decision both halves of the pair have said yes to — a goal with acceptance criteria, and one document type, grounded in the suite's index.

Step 1 · of 9YOU

State the goal and the acceptance criteria

Say what the document is for and what must be true when it is finished. This is the intake — before any writing, before any template is opened.

done when: the goal and its acceptance criteria exist in writing, in the conversation.

Step 2 · of 9THE SESSION

State the skill's own recommendation

From context alone: which document type fits, and the approach it would take. A recommendation, made before the index is consulted — not after.

done when: a type and an approach are on the table, named as the skill's recommendation.

Step 3 · of 9THE SESSION

Ground the type decision in the index

Read the suite index — assets/templates/index.json — and match the recommendation against what is listed. The index is normative for discovery; the decision points at it, not at vibes.

the suite calls this: Index-first

done when: the type decision points at an index entry — or its absence is named out loud (decision 02).

Step 4 · of 9YOU

Confirm the type

You say yes to one type. Where two candidates could both carry the document, this confirmation is not a formality — it is the decision (decision 01).

done when: you have confirmed one type, in the conversation, before anything is copied.

Phase 01 checklist · four boxes, all ticked before phase 02

  • Goal + acceptance criteria — stated by you, in writing.
  • Recommendation made — type + approach, from the session, before the index was read.
  • Index consulted — the decision grounded in assets/templates/index.json.
  • Type confirmed — by you; one type, said yes to.
?
Decision 01 · at the exit of ask & align — if two types could match

The session asks; you confirm before anything is copied.

Two plausible types is not a tie to break silently. The session lays both entries side by side, you pick one — and only then does the build phase open the template.

?
Decision 02 · at the exit of ask & align — if no type matches

The extension protocol applies.

The suite grows instead of the document bending: the session builds the unlisted type to the same conventions, saves it, registers it in the index, bumps the suite version and writes its own changelog line — the next run finds it in the index.

Phase 02 · Build 2 steps · all the session's — you wait, holding the confirmed type

Instance the template, render the figures

The build phase is the session's alone, and it is deliberately short: copy, swap, render. Nothing here invents a layout — the template is the layout.

Step 5 · of 9THE SESSION

Instance the template

Copy the confirmed template and swap its self-describing placeholders for the real facts — preserving the layout, the interactions and the Clay tokens. The instance changes content, never design.

the suite calls this: Template instance

done when: every placeholder is swapped and layout, interactions and tokens are untouched.

Step 6 · of 9THE SESSION

Render the figures

Mermaid sources rendered by pele at build time (Node), clayified, inlined as SVG on Clay variables inside a fenced plate with its FIG · NN caption. Zero network requests survive the build.

the suite calls this: Figure · pele

done when: each figure is inlined SVG on Clay tokens, in its plate, with its caption.

Phase 02 checklist · three boxes, all ticked before phase 03

  • Template copied, not redesigned — layout, interactions and Clay tokens preserved.
  • Placeholders swapped — real facts in, self-describing placeholders out.
  • Figures built — pele-rendered, clayified, plated, captioned.
Phase 03 · Check 2 steps · shown first, judged second

Show it, gate it, fold in the feedback

The document looks done from the inside; this phase proves it from yours. The session shows, you judge — and nothing downstream of this phase moves until the gate says so.

Step 7 · of 9THE SESSION

Show the document in the browser

The playback: the finished instance opened where you read it — light and dark, scrolled whole, folds and jumps working. The session does not summarize it; it shows it.

the suite calls this: Playback

done when: the document is open in your browser and you have seen it whole.

Step 8 · of 9YOU

Pass the review gate

You approve — or you say what is wrong. Feedback goes back into the build and the document is shown again. Approval is yours to give; it cannot be assumed.

the suite calls this: Review gate

done when: you approve — or your feedback has been folded in and the document shown again.

Phase 03 checklist · three boxes, all ticked before phase 04

  • Shown in the browser — the whole document, not a description of it.
  • Feedback folded in — every round of it, each followed by another showing.
  • Gate approval given — by you, out loud.
?
Decision 03 · at the exit of check — if the gate fails

Feedback is folded in; nothing builds forward.

A failed gate does not demote the document to "good enough for storage" — the run holds at this phase until a re-show earns your approval. Storage waits; it is the next phase, not a consolation prize.

Phase 04 · Keep 1 step · your choice — four options, the specified one wins

Choose the home, close the run

One step, four options, zero defaults. The document lands where you choose — and "nowhere yet" is a legitimate choice, as long as it is made on purpose.

Step 9 · of 9YOU

Choose from the storage menu

(a) the project docs folder — <project>/docs/<YYYY-MM-DD>-<slug>.html; (b) the central collection — E:\te9-docs\documents\; (c) preview only; or (d) specify a location — which always wins when used.

the suite calls this: Storage menu

done when: the document sits at its chosen home — or the run closed as preview-only, on purpose.

Phase 04 checklist · three boxes, all ticked before the run closes

  • An option named — a, b, c or d, chosen by you.
  • Used = chosen — the location used is the location chosen; a specified location always wins when used.
  • Ledger marks, if a new type was built — index entry, version bump, changelog line (decision 02's tail).
Definition of done

Four conditions, none optional

The run is finished when all four lines below hold. Three of four is the most common way a document fails without anyone noticing — usually the fourth.

The whole run, passed4 conditions · 1 conditional · 0 assumptions

A document is done when all four hold — not three, and not "basically".

01 · Goal met

The acceptance criteria from intake are met — checked against the criteria named in phase 01, not against a mood. The goal the run opened with is the goal the run closes on.

02 · Gate passed

You approved the document in the browser — after seeing it whole, with every round of feedback folded in and re-shown. No approval, no done.

03 · Storage chosen

The document sits at its chosen home — project docs folder, central collection, a location you specified, or preview-only as a deliberate close.

04 · Registered if new type

Only when the run built an unlisted type: the index entry exists, the suite version is bumped, the changelog line is written. Runs that used a listed type skip this line — done is still done.

Then the run closes · nothing pending, nothing assumed — the next document starts a fresh set of empty boxes
