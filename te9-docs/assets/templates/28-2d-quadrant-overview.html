The method

Two axes, four corners — and what each corner means

A quadrant chart is read corner-first: the axes draw the map, the corners carry the meaning, the points only inherit it. So the method comes before the residents — what each axis prices, and what each corner concludes — stated before any position is read.

The method · baseline v2.5.0 · 27 of 35 landed, counted

Build effort against reader impact — the reading is in the quadrants.

The x axis is build effort: structural novelty × figure complexity — what a fresh, gated build of the type would cost, its figure renders and review round-trips included. The y axis is reader impact: how central the type is to the suite's promise — shareable, polished, single-file documents a human actually forwards. Four corners fall out of the two axes, and each means something: top-left, build first — core impact at affordable effort; top-right, plan carefully — core impact, but heavy; bottom-left, quick wins — cheap to land, niche in reach; bottom-right, defer — the heaviest builds serving the narrowest readers. The three landed anchors sit on the chart to prove the axes can place known cases where the suite already knows they belong.

What the axes deliberately do not measure
Three things the plot leaves out — on purpose
  • Clock hours. The founding day built 25 templates in one sitting, so history cannot price a type — the x axis argues what a fresh gated build should cost, not what once went fast. The effort model's own forward rate (≈1–1.5 h per gated template, per the rolling forecast) is where the clock re-enters.
  • Sequencing between types. The corners say what to build first in aggregate; dependencies that force a finer order (the index before the pages it links, say) live in each corner's consequence strip, not in the plot coordinates.
  • Reader taste. The y axis prices centrality to the suite's promise, not how much any one reader will love a type. A niche corner is a small audience, never a verdict on the reading.

Quadrant · build first

Core impact, affordable effort

Why the medium types read right of center
The midline argument — the judgment, in the open

"Medium" is the middle band, and the vertical midline cuts through it — so a medium type lands where its argument pushes it. Two mediums sit right of the line here, for the same reason: the link/dependency analysis and this quadrant chart both arrive with figures already native in pele, but each introduces an analysis layout the suite has never drawn — blast-radius reading, corner semantics, a legend grammar. New prose structure, not just new charts, is what the x axis prices heaviest.

The Decisions log, the mirror case, sits left of the line for the mirrored reason: its kanban grammar was pele-native and its layout (one card per decision) was already the suite's card grammar — nothing new but the discipline.

Consequence · build order
Sequence, don't sprint: link/dependency analysis first of the three open builds (its figures are native types), then wikipage + index (its index defines the cross-links the tutorial will reuse), then the tutorial last — the heaviest build, benefiting from everything the cluster hardened before it. One gated build per round-trip; no batching.
