The concept set

Six concepts, each with its own identity

Each panel below carries the glossary definition word for word, the reason the concept exists, its sibling relationships, and — folded open — one worked example drawn from the suite's own records. Definitions are quoted; the examples are real.

Concept 01 · The artifact

Document

A single self-contained HTML file produced by te9-docs for human readers outside the building session — the deliverable, never a scratch file.

Why it matters. Everything the suite makes is one of these: polished, shareable, zero network requests, readable by a person who was never in the session. If an artifact isn't fit to hand to a reader, it isn't a Document — and the suite doesn't ship it.

Storage menu, option (a)

A produced Document is offered the storage menu after playback: save to the project docs folder as <project>/docs/<YYYY-MM-DD>-<slug>.html, save to the central collection (E:\te9-docs\documents\), keep as preview only — or option 4, specify location, which always wins when used.

Concept 02 · The unit

Template

A complete, finished, polished HTML document with realistic placeholder content — not a skeleton, not a component kit. The unit of the suite.

Why it matters. Templates are the suite's inventory: the launch taxonomy counts 36 — the three founding documents plus 33 additional types, this one among them. Because each Template is finished to Clay standard, the Index that lists them doubles as the suite's manual.

Worked example · the founding trio
Conversion, not invention

The suite's first three Templates — brief.html (decision brief), dossier.html (evidence dossier), deck.html (presentation deck) — were converted from the founding examples at E:\te9-docs\docs\examples, their placeholders rewritten to document the suite itself. Every later Template follows the same shape.

Concept 03 · The mechanic

Template instance

A Document produced by copying a Template and swapping placeholder content for real content while preserving layout, interactions, and visual design. The core production mechanic — adopted as-is from html-docs.

Why it matters. No document is built from scratch. A production run grounds its type choice in the Index, copies the chosen Template, and swaps content — layout, interactions and Clay tokens stay untouched. That is what keeps the 36 types one publication instead of 36 private styles.

Concept 04 · The first step

Intake

The mandatory first step of every production run, before any writing: the session asks for the document's goal and acceptance criteria, then states its own recommendation — suggested document type and approach — derived from the context it already has. The user confirms type before building.

Why it matters. Intake is the guard against the wrong document, beautifully made. The suite has an opinion — it recommends a type from context — but the reader's goal and acceptance criteria come first, and the type is confirmed before a single line is written.

Worked example · how an Intake runs
Workflow, step 1

A session is asked for "a report". Intake asks back: what is the document's goal, and what are the acceptance criteria? The session then states its own recommendation — suggested type and approach — from the context it already has, and the user confirms the type before building. The confirmed goal + criteria become the contract the finished Document is reviewed against at playback.

Concept 05 · The approval

Review gate

The build-step approval rule: after each template is built, it is shown in the browser (or file path named) and the user approves or gives feedback; nothing is built forward until the gate passes. Feedback applies to the current template AND the conventions for all later waves.

Why it matters. The gate is how one template's review improves its neighbors: the 36 types are built in sibling groups — build clusters — so feedback on one template immediately benefits the next. Without the gate, drift ships; with it, conventions converge.

Workflow, step 5

A freshly built template is shown in the browser; feedback is folded in on the spot. Nothing is built forward until the gate passes — and because the suite builds in sibling clusters, a fix agreed at this gate is written into the conventions every neighboring template inherits.

Concept 06 · The growth engine

Extension protocol

How the suite grows in normal use: when a session needs a document type not in the suite, it builds the Template autonomously — Clay conformance, self-describing placeholder content, script-whitelist compliance — registers it in the index, and bumps the suite version, all without asking. The user discovers new types in the index next session.

Why it matters. The protocol makes every session an author: no gatekeeper, no staging area, no one-off bespoke documents. Growth is autonomous but never unconforming — the preconditions produce siblings of the founding trio, and the suite version records each arrival.

Worked example · how an extension bumps the version
The protocol, at work

A session needing an unlisted type builds the Template to the same conventions — Clay, self-describing content, whitelist compliance, quality gates — saves it to assets/templates/, registers it in assets/templates/index.json, bumps the suite version, and writes its own one-line changelog entry. Versioning is semver: new Template = MINOR, template or convention fix = PATCH, breaking = MAJOR. The template you are reading is the protocol at work — the first type designed fresh after the founding trio's conversion.

How they fit together

The run order

Read the six concepts as one sequence: what a production run executes, in order, from the first question to the stored Document — plus the loop that runs when the set itself is not enough.

  1. 01

    Intake — before any writing

    The session asks for the document's goal and acceptance criteria, then states its own recommendation — type and approach — from context. The user confirms the type before building.

  2. 02

    Index-first — ground the type decision

    Read the suite index (assets/templates/index.json) and ground the type decision in it; confirm with the user if two types could match.

  3. 03

    Instance — copy the Template, swap the content

    Copy the chosen Template and swap self-describing placeholders for real facts, preserving layout, interactions, and Clay tokens. Concept 03 is this step.

  4. 04

    Review gate — nothing builds forward until it passes

    Show the document in the browser; approve or fold in feedback. Feedback applies to the current template and the conventions for all later builds.

  5. 05

    Storage menu — where the Document lands

    Project docs folder, central collection, or preview only — with option 4, specify a location, which always wins when used. The Document is then out of the session's hands and in a reader's.

  6. 06

    The loop — when no type fits

    If the Index lists nothing suitable, the Extension protocol runs: build the Template to convention, register it, bump the suite version, write the changelog line. The user discovers the new type in the index next session.

Six steps, six concepts, one invariant: the produced artifact is always a Document worth handing to a reader — and the suite that produces it only ever grows by becoming more of itself.
