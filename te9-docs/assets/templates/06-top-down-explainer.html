Level 3 · Pillar 01

The Clay design system

Clay Explainer — the suite's one design system: warm ivory paper ground, 1.5px hairlines, mono pill kickers, giant serif headlines with one italic clay word, and fenced gray-100 figure plates with mono FIG · NN captions.

The system is specified in references/CLAY-STYLE.md, extracted from the founding examples. Accent discipline is baked in: raw clay #FE6C2D is decorative-only on light ground — borders, rings, icons — and every piece of accent text retunes to --clay-ink #B8430F for AA contrast. Olive and rust support it, each with ink and soft variants.

Three system faces, zero webfonts: ui-serif display, system-ui body, ui-monospace micro-labels — which is why every document ships with zero network requests. And under Clay discipline, zero scripts by default: <details> folds, :target jumps and hover states carry every interaction, with anything more needing the script whitelist.

Level 4 · why the orange never carries text
The retune, in one number

Raw clay on ivory measures 2.69:1 — fine for a ring, illegible for a sentence. So the palette carries two clays: the raw one for everything decorative, and --clay-ink #B8430F, at 4.70:1 or better everywhere it carries text, for every word. In dark mode the relationship flips and clay itself becomes AA text again — one token flip, no redesign.

Level 3 · Pillar 02

The production workflow

A production run is the suite's six-step workflow — intake before any writing, storage only after approval.

1 · Intake asks for the document's goal and acceptance criteria, and states the skill's own recommendation — type and approach — from context. 2 · Index-first reads the suite index (assets/templates/index.json) and grounds the type decision in it, confirming with the user if two types could match. 3 · Instance copies the Template and swaps its self-describing placeholders for real facts, preserving layout, interactions and Clay tokens.

4 · Figures renders Mermaid through pele at build time into inline SVG in Clay variables. 5 · Playback — the Review gate — shows the document in the browser and folds in the reader's feedback. 6 · Storage menu offers the finished Document its place to live.

Level 4 · the storage menu's fourth option always wins
Precedence, not preference

The menu: (a) the project's docs folder, (b) the central collection, (c) preview only — and (4th) specify a location, which always wins when used. The fourth option is not a fourth peer but an override: a reader who names a path ends the menu in one move, and the Document goes exactly there.

Level 3 · Pillar 03

The launch taxonomy

Launch taxonomy — 36 templates: the three Founding documents plus 33 additional types, from introduction of concepts to tutorial.

The Founding documents came first: brief.html (decision brief), dossier.html (evidence dossier) and deck.html (presentation deck), converted from the examples with their placeholders rewritten about the suite. Around them stand the 33 additional types — introduction of concepts, concept breakdown, top-down explainer, standard operating procedure, API documentation, tutorial, and more.

Discovery runs through one machine-readable registry: the Index at assets/templates/index.json, generated from the template directory and normative for type decisions — no keyword heuristics file.

Level 4 · this document is one of the 33
Self-describing, literally

Top-down explainer is named in the taxonomy — and this Template is that type, documenting the suite with its own grammar. When a session needs a type the taxonomy lacks, it does not wait: the growth protocol below turns the gap into the next registration.

Level 3 · Pillar 04

The autonomous growth protocol

Extension protocol — fully autonomous: a session needing an unlisted type builds it to the same conventions and registers it itself.

The protocol is a fixed sequence: build the new type to the suite's conventions — Clay, self-describing content, whitelist compliance, quality gates — save it to assets/templates/, register it in the Index, bump the Suite version, and write the session's own changelog line. The user discovers new types in the Index next session.

Growth is how this document exists: this top-down explainer reached the suite through the same protocol it describes.

Level 4 · what each version bump means
Semver, stamped in the brief

The Suite version is semver MAJOR.MINOR.PATCH: a new template bumps MINOR, a template or convention fix bumps PATCH, a breaking change bumps MAJOR. Every bump appends a one-line changelog entry — the version number is the suite's own top-down summary.
