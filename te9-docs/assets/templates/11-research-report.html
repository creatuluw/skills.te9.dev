Research Report

One figure, three renders, five fixes

The research question: how does a Clay figure render across environments? One inline SVG leaves the build pipeline and passes through three render environments — live Chrome with document CSS, headless screenshot capture, and the sharp/librsvg rasterizer that encodes video frames. This report compares the three and reports the five failure modes the comparison surfaced — each with the root cause beneath it and the fix that closed it.

The method

Three environments, four moves

The investigation ran without instruments beyond the pipeline itself: every figure was observed in each environment it must survive, failures were hunted at frame level, and no finding was accepted until a fix had been applied and the whole loop rerun clean.

01 Three environments

Every figure observed in live Chrome with document CSS, in headless screenshot capture, and in the sharp/librsvg rasterizer for video export — the full journey of one figure.

02 Frame-level inspection

No environment was sampled. Frames were inspected at frame level, because a figure counts as correct only when every environment paints every frame right.

03 Render-and-compare

Iterative by construction: render, set the environments side by side, and record every delta against the live browser's paint — the reference render.

04 Fix-and-rerun

A finding closed on verification, never on argument: the fix landed, the full loop reran, and only a clean re-render across all three environments earned the Fixed chip.

The comparison in one map

The findings

Five failure modes, all closed

Each panel is one finding in discovery order: what was observed and in which environment, the root cause beneath it, and the fix that closed it — with the verification folded open beneath. Every chip below reads Fixed, and each one was earned by a rerun, not by confidence.

Finding F1 · Theming Fixed · v0.2.3

The indirection that painted chips black

Observation

CSS classes plus var() indirection inside the inline SVG's <style> painted edge-label chips black in some contexts — while the same figure painted correctly in the live browser.

Root cause

The variables were resolved through document CSS in some contexts and not at all in others; where nothing resolved them, the chip's fill fell through to ink.

Fix

Variables are resolved via document CSS — Clay tokens mapped onto the figure's variables on the plate — and, for rasterizers, explicit Clay hex substitution.

Verified by · the rerun that closed it
Fix-and-rerun · F1

With the mapping moved into document CSS and the rasterizer path switched to explicit hex, the same figure was re-rendered through all three environments. The edge-label chips painted identically in each — this document's own figure carries the fix.

Finding F2 · Sizing Fixed · v0.4.4

The inline style that overruled the stylesheet

Observation

pele's inline style attribute on the SVG root — max-width/height — overrode the document's CSS sizing rules, and no rule the stylesheet declared could win.

Root cause

Inline style outranks document CSS by design; any sizing the document declared was dead on arrival against an attribute the reader never sees.

Fix

clayify normalizes sizing — the inline sizing is normalized away so that CSS governs, as the plate grammar intends.

Verified by · the rerun that closed it
Fix-and-rerun · F2

After the normalization landed, the plate's sizing rules held in every environment: the figure rendered at its natural reading size, shrinking only to fit — no attribute overruling the stylesheet anywhere in the loop.

Finding F3 · Text Fixed · v0.4.6

The labels only the live browser painted

Observation

Headless screenshot capture dropped weight-600 monospace SVG labels in complex figures, while the live browser painted the very same labels without complaint.

Root cause

The labels were styled by class only — and the headless capture resolved some class styling and not others, making class-only styling a single point of failure.

Fix

Labels now carry presentation attributes — font, size, weight, fill — instead of class-only styling, so the paint travels with the element.

Verified by · the rerun that closed it
Fix-and-rerun · F3

The most complex figure in the suite was re-captured headless with attrs-backed labels: every weight-600 monospace label present in every frame, matching the live browser's paint. The labels in this figure are the fixed kind.

Finding F4 · Buffers Fixed · video exporter

The quarter of the frame stream that vanished

Observation

In the video exporter, raw pixel buffers became 3-channel while the encoder pipe still declared 4-channel — a quarter of the frame stream silently lost, no error raised.

Root cause

flatten() drops the alpha channel, and nothing upstream told the encoder that the channel count had changed under it.

Fix

ensureAlpha() after flatten() — the buffer's declared shape and its actual shape agree again, end to end.

Verified by · the rerun that closed it
Fix-and-rerun · F4

The exporter reran with the alpha restoration in place: the buffers moving through the pipe matched the 4-channel declaration at every joint, and the encoded frames carried the full stream.

Finding F5 · Geometry Fixed · video exporter

The height recomputed from the wrong source

Observation

In the rasterizer, canvas height was recomputed from the viewBox when it should have come from the declared dimensions — frames left the pipe at the wrong height.

Root cause

Once clayify extends the canvas for label overhang, the viewBox and the declared dimensions disagree; a rasterizer reading the viewBox gets a different answer than one reading the dimensions.

Fix

resize() forces the exact frame dimensions — the declared numbers win, and nothing recomputes them from the viewBox.

Verified by · the rerun that closed it
Fix-and-rerun · F5

With the resize forcing exact dimensions, rerendered frames came out at precisely the declared height in the raster path — the extended viewBox no longer leaks into frame geometry.

The conclusion

The contract the failures wrote

Five failures across three environments, and not one of them random. Read together, F1–F5 are a single lesson: a figure that must survive three environments cannot owe its paint to any single one. What the investigation produced is not a patch list but a contract — four clauses every Clay figure now ships under.

01 · Attrs-backed labels

What must paint everywhere — labels above all — carries presentation attributes: font, size, weight, fill. Class-only styling is hope, not paint.

02 · CSS-owned theming

The Clay mapping lives in the document's stylesheet, resolved via document CSS; the SVG never carries its theme inline, and rasterizers get explicit hex.

03 · Explicit dimensions

Width and height are declared and enforced with resize(); nothing recomputes frame geometry from the viewBox after the canvas is extended.

04 · Alpha preserved

flatten() never strips a channel the encoder still promises — ensureAlpha() keeps the stream 4-channel from first frame to last.

Recommendations

Three rules for the next pipeline

The contract, compressed into the three rules this suite now works by. Each is imperative on purpose: these are the checks that would have caught F1–F5 before a reader ever saw them.

R1 Verify in the real browser

The live browser is the reference paint. No headless or rasterized render counts as verified until it matches what Chrome painted.

R2 Never trust var() in rasterizers

A rasterizer brings no var() engine. Anything it must paint arrives as explicit Clay hex, never as an indirection.

R3 Assert buffer sizes

Declare the frame dimensions and the channel count, then assert both where the pipe's stages meet. Silence is not agreement.
