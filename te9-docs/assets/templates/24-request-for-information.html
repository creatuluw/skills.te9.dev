Section 1

Background

te9-docs is a document-suite skill: it produces polished, shareable, single-file HTML documents for human readers. At suite version 2.0.0-rc2 it ships 23 templates in one design system — Clay Explainer — under a discipline of zero webfonts, zero network requests and zero scripts beyond one whitelisted fullscreen listener. Every template earns its place through a browser review gate: a human opens the file and checks it against the style reference before it ships. That gate is the suite's entire quality apparatus — and this RFI exists because it does not scale.

GateWhat it verifiesHow it runs today
ContrastText tones against their grounds — guardrails were computed into the style reference at design time (all text ≥ 4.5:1).Checked by eye at review, against the computed table.
Dark flipThe prefers-color-scheme token flip across every panel, chip, table and figure.One OS toggle, paged through manually per template.
PrintThe A4 print spec: folds forced open on paper, light palette regardless of OS theme, no component split across pages.Print preview, eyeballed page by page.
Zero networkNo requests beyond file:// — system fonts only, no webfonts, no trackers.DevTools network tab, watched by hand on every review.
Figure collisionsPele figures against their outside labels, legends and plate edges.Seen at a glance — or missed.
In sumFive gates, every template, every build — all manual, all visual, all human-hours.

Before considering a solicitation for automated QA tooling — a possible RFP-2026-02 — the suite surveys the market: what is mechanically checkable today, with what reliability, at what cost. This document asks for that information. The answers educate the issuer; they commit no one.

Section 2

Area of interest

Four groups, twelve questions. Answer any subset, in any order, for any group — a response that says “we tried it and it did not hold up” is as useful as a success story. This is a survey, not a test: there are no scores, and nothing here can be won or lost.

01

Design-token conformance

static CSS analysis
Q1.1

How do you programmatically verify CSS custom-property conformance across many standalone HTML files — parsing declarations, resolving var() chains, diffing the result against a token reference?

Q1.2

Which tooling have you actually run for this — stylelint plugins, PostCSS passes, custom AST scripts — and what did it cost to keep the checks honest as the token set evolves?

Q1.3

Where does static analysis end for you: which token violations only a rendered browser pass catches in practice?

02

Accessibility automation

engines vs human review
Q2.1

What share of WCAG 2.2 AA issues do axe-core, pa11y and Lighthouse reliably catch on static HTML pages — and what do they miss that still needs human review?

Q2.2

How do you run those engines at scale across a folder of standalone documents — no build step, no dev server — and merge their reports into one usable signal?

Q2.3

How do you audit prefers-color-scheme: dark variants automatically: two forced passes, browser emulation, or something else?

03

Print-output audit

paged media, mechanically
Q3.1

Can print rendering be captured and compared automatically — headless Chrome --print-to-pdf, page screenshots, pixel or structural diffing — and how noisy is the diff in practice?

Q3.2

Which print defects has that caught for you — page breaks, forced-open folds, missing content — and which does it reliably miss?

Q3.3

Is PDF output a faithful proxy for the browser's own print path in your experience, and how do you handle A4 versus Letter without duplicating everything?

04

Integration

CI for a zero-build suite
Q4.1

How do such checks fit continuous integration for a static, zero-build document suite — what triggers a run, and what runs on every commit versus on a schedule?

Q4.2

What does the result surface look like: pass/fail gate signals, per-document reports, a dashboard a single maintainer can actually read?

Q4.3

What is the realistic running cost: flake rate, false positives, and the maintenance burden of keeping the checks in tune with a design system that changes?

Section 3

Response guidelines

A response is information, not an offer — and it will be read as a survey answer, not as a bid. Send anything that helps: a page of rough notes teaches more than ten polished pages that say nothing. File via the repository issue tracker with the label rfi-2026-01, by 2026-11-26. A useful response ticks these boxes:

C-1

Keep it short or link it. At most 5 pages of PDF or Markdown — or a public repository link that answers the questions in situ. Effort spent on formatting is effort wasted.

C-2

Name the tools. Concrete names and versions you have actually run — not categories. “A linter” teaches nothing; “stylelint with a custom rule for undeclared custom properties” teaches.

C-3

State the honest limitations. What your approach misses, how often it false-positives, what still needs a human. Limitations are the most valuable lines in a survey.

C-4

Size the integration effort. What adopting your approach would mean for a static, zero-build suite: dependencies, scripts, CI minutes, ongoing maintenance.

C-5

File it right. One issue on the tracker, label rfi-2026-01, title RFI-2026-01 — <your name or org>, by 2026-11-26. Late answers may miss the summary, but nothing is refused.

Section 4

What happens next

Four steps, honestly stated. The last one is possible, not promised — and every earlier step is informational only.

01

Responses are read and summarized. Quotations are anonymized unless a respondent explicitly asks to be named.

02

The summary is published to the same tracker, and the area of interest is reshaped by what it finds — the questions above are a draft of the suite's ignorance, not a fixed scope.

03

The summary informs whether a future RFP-2026-02 for automated QA tooling is issued — the dashed ring in FIG · 01. It may equally conclude that manual review is good enough. No respondent is favored by having responded.

04

No contract arises from this RFI. Responding creates no obligation on either side, and this document awards nothing, scores nothing and commits to nothing.

Drawn, the survey is one chain: the RFI issues (filled — here-now), responses arrive, the summary is published. The fourth ring is a double ring on a dashed edge because it is only possible — a future solicitation that the responses themselves will justify or dissolve.
