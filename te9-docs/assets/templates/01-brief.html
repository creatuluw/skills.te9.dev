Frame

The question, the rails, and what we optimize for

The question: with the founding trio settled in Clay and the index live at v0.1.0, in what order should the remaining thirty-three types be built so the suite reaches v1.0 without breaking a single rail?

Constraints — the rails

  • C1The review gate is absolute — nothing builds forward until the current template passes in the browser.
  • C2Clay discipline everywhere — zero scripts beyond the whitelist, one shared palette.
  • C3Placeholder content documents the suite itself; SUITE-BRIEF.md is the only assertable source.
  • C4The index is normative — every type lands in index.json with a suite-version bump.
  • C5html-docs stays untouched — patterns adopted one by one, with an explicit adopt/adapt/reject verdict.

Criteria — weighted

  • ×3Gate compounding — feedback on one template should benefit its neighbors
  • ×2Gate honesty — the gate reviews one template, not a pile
  • ×2Launch predictability — v1.0 arrives in a knowable order
  • ×2Review economy — gate cost amortized, not paid per file
  • ×1Scheduling simplicity — the run is plannable without weekly renegotiation

Options

Three doors, each with its own kill switch

OPTION A

Build clusters — sibling groups

The 33 types constructed in similarity groups — explainers with explainers, reports with reports — so gate feedback on one template lands in its neighbors the same session, not a rediscovery per file.

Gate per templateFounding trio first

Killed if — a cluster needs a convention change that would ripple through templates already passed.

OPTION B

Fixed batch waves

All 33 types on a calendar: each batch built in sequence, then reviewed together at one shared gate. No sequencing decisions left after launch day is scheduled.

One review per batchCalendar-driven

Killed if — a shared gate must pass a pile; nothing may build forward on an unpassed template.

OPTION C

Extension-only, on request

Build nothing speculative: each template grows when a session needs the type, through the extension protocol — build, register, bump the version, log the change.

No speculative buildsGrows with use

Killed if — the launch taxonomy must be complete; on-demand building never reaches thirty-six.

Verdict

One order ships; one fails the gate; one waits — for after launch

A · Build clusters — sibling groups, one review gate at a time, launch at v1.0.

  • It is the only option that clears every rail at once: a dedicated gate per template, self-describing siblings sharing one Clay palette, and the index filling in a reasoned order.
  • Sibling groups turn gate feedback into an asset — a fold-grammar fix found in the explainers is applied to its neighbors before the next gate, not rediscovered per file.
  • The last cluster completes the launch taxonomy and hands growth to the extension protocol (ADR 0006): after v1.0, new types are built on request, autonomously, with their own changelog line.
Runner-up — where B stands, and why it fails the gate

Runner-up — B scores well on predictability and scheduling but fails constraint C1 outright: a batch cannot pass a shared gate without building forward on unpassed templates, and batch review is exactly the anti-pattern the review gate forbids. C is not rejected on merit — it loses on review economy and launch completeness, and becomes the norm the day after v1.0 as the extension protocol (ADR 0006).

Risks

Named, owned, pre-mitigated

Risk · sibling driftTemplates built sessions apart drift off the shared Clay palette and interaction grammar.
Mitigation · owner: Build sessionEvery build reads SUITE-BRIEF.md and the index first; the gate reviews against Clay Explainer tokens, and drift found in one sibling is fixed in its neighbors before the next gate.
Risk · convention change mid-launchA whitelist entry or intake rule evolves after some clusters have already passed.
Mitigation · owner: Founding sessionConvention fixes are PATCH bumps with a changelog line, and affected gates are re-run rather than grandfathering passed templates.
Risk · index stalenessA template that passes its gate but is never registered makes the index lie to the next session.
Mitigation · owner: Build sessionRegistration and the version bump are one step at the gate; the next intake reads the index first, so a missing row surfaces immediately.
