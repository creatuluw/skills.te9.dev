Why sequences carry the meaning

Schedule view4 timelines · 24 steps · every output hands forward

A suite is a set of promises about order — each process is a timeline, each timeline is steps in sequence, and each step exists to hand its output to the next.

Timeline

A process with a fixed shape: numbered stops on a track, in the order the work actually runs. The suite has four — the production run, the template build, the extension protocol, the video export.

Step

The unit of the grammar. Every step card carries the same three facts — the trigger that starts it, the effort it costs (an estimate, labeled), the output it hands forward. Where a step maps to a real suite term, the card names it.

Output

The reason the order is not decoration: a step's output is the next step's input. Break the sequence and the intake never grounds in the index, the figure never meets the gate, the document never finds a home.

States

None drawn. This is a schedule view, not a player — the tracks show when and in what order, never what is done. A filled ring here would be a claim about now, and this page does not make it.

Estimates

No calendar governs this suite, so no duration here is a measurement. Every ≈ number is an honest estimate, labeled as one — and the video export's are flagged as guesses outright.

Read on · the production run first — the timeline every document travels

Estimate method · where every ≈ comes from
Judgments made at build time — not stopwatch numbers

Production run: per-document figures — intake and playback are conversation-length, instance and figures are the build's core, storage is mechanical.

Template build: once per type — the brief-and-sibling read and the figure pipeline dominate; the registration tail is minutes.

Extension protocol: inherits the template build's shape — its own five steps add detection plus the registration marks.

Video export: guesses, twice over — the pipeline is parked, so no estimate here has ever been checked against a full run.

When a real calendar matters, this document is the wrong tool; the timelines describe order, not schedule.

The extension protocol

  2. 2Build to conventions
  3. 3Save numbered file
  4. 4Regenerate index
  5. 5Bump + changelog
Step 01≈ minutes · est.

Detect the unmatched need

Trigger

A session needs a type the index does not list.

Output

The need named and the decision made — extend the suite rather than force-fit an existing type.

Step 02≈ 1 build · est.

Build to the conventions

Trigger

The need is named and owned.

Output

The new type built to Clay discipline — self-describing content, whitelist compliance, quality gates.

the suite calls this: Clay discipline

Step 03≈ seconds · est.

Save the numbered file

Trigger

The build passes its gate.

Output

The template saved to assets/templates/, numbered into the directory's sequence.

the suite calls this: assets/templates/

Step 04≈ seconds · est.

Regenerate the index

Trigger

The file is saved.

Output

index.json regenerated from the template directory — normative for discovery, never hand-edited.

the suite calls this: Index

Step 05≈ 2 min · est.

Bump the version + log it

Trigger

The index is regenerated.

Output

The suite version bumped, one changelog line appended — the next session discovers the type in the index.

the suite calls this: Suite version · changelog

Sequencing note · timeline 03 wraps timeline 02: steps 01–02 travel the template build's track, steps 03–05 are the registration tail the build's own step 07 performs from the inside. One session does all of it — the protocol is autonomous by design.

Step 06≈ seconds · guess

Status note · this timeline is parked. The changelog's eight unit tests cover step 02's frame function and nothing else — the pipeline downstream of it (raster, flatten, ffmpeg pipe) is the experiment's design, drawn here as a schedule, not a claim. Hence the chip: every ≈ on this track is a guess, and says so.
