DEC-07 ADR-0007 2026-10-29 Believe

All figures render through pele — the hand fallback shrinks to true impossibility

Every figure is Mermaid source rendered through pele at build time; hand-authoring an SVG is allowed only when pele cannot express the diagram type at all.

The reasoning

A user verdict at gate #4 — "I can't imagine we can't draw a similar diagram with Mermaid via pele" — was tested and confirmed: pele renders circle nodes, double circles, classDef strokes and edge captions. The earlier session learning had overstated the case; what pele gives up is pixel-level composition control, not the Clay ring grammar itself.

ConsequenceFills stay transparent so the dark flip keeps working, "double ring" replaces "filled = deliverable", and every hand-authored exception must argue its impossibility at the review gate. This supersedes the fallback clause of ADR-0005.

DEC-06 ADR-0006 2026-10-29 Believe

The suite grows autonomously: extensions register themselves without asking

A session needing an unlisted type builds it to convention, registers it in the suite index, and bumps the suite version — no proposal step, no staging area.

The reasoning

Every extension already passes the full conformance discipline — Clay, self-describing content, quality gates — the same discipline every launch template passes, which the user reviews continuously anyway. A request-approve round-trip bought nothing extra: a plan cannot be evaluated better than the finished artifact.

ConsequenceThe index changes without warning, so sessions consult it at each run. Misfits are discovered in the wild but stay user-inspectable, editable and removable; the changelog line and version bump on every extension are the audit trail of autonomous growth.

DEC-05 ADR-0005 2026-10-29 Superseded

Diagrams render through pele at build time; documents stay single-file and offline

Diagrams are authored as Mermaid text and rendered with pele once at build time, inlined as static SVG — no runtime, no CDN, no diagram JavaScript.

Superseded by ADR-0007 — the hand-authored fallback this record allowed is gone; see DEC-07.

The reasoning

Runtime mounting from a CDN breaks the zero-network, file:// offline contract; hand-authoring 50-arrow diagrams is error-prone. This record replaced html-docs' pretty-mermaid pipeline and its vanilla-JavaScript pan/zoom viewer, both rejected patterns for the suite.

ConsequenceNode and the pele package became production-time dependencies of the skill — never of a finished document. ADR-0007 kept this record's build-time rule and removed its fallback clause, shrinking hand-authoring to true impossibility.

DEC-04 ADR-0004 2026-10-29 Believe

Clay discipline is the default; real JavaScript requires a published whitelist

Suite documents default to zero scripts — <details> folds, :target jumps, hover states — plus the deck's single sanctioned navigation script.

The reasoning

A pure zero-JavaScript rule would decay or be bypassed invisibly: some of the 33 additional types — API documentation, data report, editor-style documents — plausibly need behavior no CSS mechanism provides. html-docs-level interactivity, meanwhile, reintroduces the patterns the suite deliberately excluded and breaks the print and offline guarantees Clay bakes in.

ConsequenceThe whitelist is normative skill content — a template with non-whitelisted scripts is non-conformant — and the print and offline guarantees stay mandatory for every template, whitelisted or not.

DEC-03 ADR-0003 2026-10-29 Believe

Placeholder content is self-describing: every template documents the suite

Each template's realistic placeholders are written about the te9-docs suite itself — the meeting-notes template records a suite planning session, the API-documentation template specs the extension protocol.

The reasoning

Dogfooding: building all 36 templates with one coherent subject exercises every structural affordance the way a real document would, and the finished index doubles as the suite's own manual. A single shared subject also makes review fast — "does this read true about the suite?" instead of "does this read true about anything?".

ConsequenceEvery build starts from a shared brief of suite facts so placeholders stay consistent across authors and sessions; content goes stale when the suite changes — the brief refresh is part of template maintenance, not a blocker.

DEC-02 ADR-0002 2026-10-29 Believe

One design system: the Clay Explainer, extracted from the founding examples

All 36 templates share one tokenized house palette and header anatomy — warm ivory ground, 1.5px hairlines, mono pill kickers, one italic clay word.

The reasoning

Adopting html-docs' ivory/slate/clay set verbatim was rejected — it ships an unretuned palette whose clay fails AA as text, which is no signature. Designing a fresh palette in-session was rejected too: the work already existed, documented, AA-checked and embodied in three reviewed example documents.

ConsequenceRaw clay is decorative-only on light ground and all accent text uses the retuned clay-ink; dark mode and the print spec are part of the system by default; templates failing the patterns checklist are non-conformant.

DEC-01 ADR-0001 2026-10-29 Believe

te9-docs is a clean-room sibling of html-docs, not an evolution of it

Build a new skill alongside the vendored html-docs — every pattern adopted from it is re-justified with an explicit adopt/adapt/reject verdict, never assumed.

The reasoning

Signature patterns require deliberate ownership. Modifying html-docs in place would muddy the provenance of a vendored skill and inherit its baggage; absorbing it into an existing doc skill would collapse two distinct concerns into one. html-docs stays untouched as a live reference for comparison.

ConsequenceThe two doc skills coexist temporarily, until a later decision deprecates one; every beneficial html-docs pattern must be consciously re-justified in te9-docs — nothing carries over on reputation.
